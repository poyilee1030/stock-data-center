# ADR-0024：TDCC 股權分散 import 路徑——內容日期為鍵、單一來源、以及兩個被來源推翻的假設

狀態：**Accepted**，隨 ROADMAP Step 24-a 合併生效。
延伸 ADR-0012（distribution profile 與 seal 完整性）與 ADR-0015 的 raw-first 生命週期；
沿用 ADR-0020 的 availability-time 政策與 ADR-0022 §8 的逐列隔離。

## 背景

Step 24-a 要把 TDCC 每週股權分散表接進 Step 6 已有的儲存契約。來源只有一個端點
（OpenData `getOD.ashx?id=1-5`，一次一個最新週的全市場檔案），但檔案的載體橫跨
2019-2026 的檔案庫，共 428 個檔案、376 個內容日期。全部解壓逐列掃過之後
（1,377,971 個 security-week，audit §4.9），有兩個既有契約假設被來源本身推翻，
還有三個匯入語意需要定案。

## 決策

### 1. 一個 dataset source，不因載體分裂

`tdcc_opendata` 同時涵蓋前向抓取與檔案庫的週。檔案庫裡的 TDCC 檔案是 OpenData
回應的完整位元組（ROADMAP §14 唯一的例外，其他領域的檔案庫都被 scraper 改寫過），
所以它們是同一個發布者的同一個序列。拆成兩個 source 會讓一個每週序列出現兩段
互不相認的歷史，而 CLAUDE.md §30 要求保存的是「不同來源」的獨立歷史，不是同一
來源的兩種讀法。載體差異記在 `artifact_origin`：檔案庫讀出來的是
`legacy_archive`，前向抓取是 `official_fetch`。

`is_canonical` 保持 false。只有一個來源，沒有東西要在來源之間選；宣告 canonical
等於宣告一個 reconciliation 政策，那要自己的 ADR（CLAUDE.md §30）。

### 2. 週的鍵是檔案自己的 資料日期，檔名只用來比對

`2020/20200619.CSV` 與 `2020/20200619.zip` 兩個檔案的 資料日期 都是 `20200612`：
它們以下載日命名，而 OpenData 當時還在供應前一週。信任檔名會憑空造出一個
2020-06-19 週，並且掩蓋真正缺少的 2020-06-20。所以 parser 以 資料日期 為鍵，
請求的週與內容日期不一致就整個檔案拒絕（`snapshot_date_mismatch`），不默默改名。
檔名日期仍然抽出來寫進 manifest，但只作為紀錄。

檔名有三種形狀（`20240105.7z`、`20201008_集保戶股權分散表20201008.7z`、
`TDCC_OD_1-5_20260918.csv`），所以比對的是「檔名中的日期」，不是「檔名等於
YYYYMMDD」。

### 3. 分級 16 存負值，人數不存

TDCC 說明4 定義這一列是「各持股分級合計股數與發行公司已發行股份總數產生之差異」。
兩件事因此成立，兩件都是驗證來的，不是推論：

* **官方的號是負的。** OpenData bulk 檔發布無號的絕對值，同一個發布者的入口網站
  把同一列呈現為負數（0056 在 2026-09-11：檔案 `28164`，網站 `-28,164`；另外
  驗過 00400A、00401A、00404A）。而且 `合計股數 = Σ 分級1..15 − 分級16` 在全部
  1,377,971 個 security-week 都成立，`Σ + 16` 沒有任何一筆成立。所以 adapter 存
  負值是引用發布者自己的呈現，不是我們發明號。若哪天檔案自己帶號，原樣通過。
* **差額沒有持有人。** 入口網站的人數格是空白，ADR-0012 也已要求 adjustment 列
  `holder_count` 為 NULL。bulk 檔固定六欄，在那一格塞了一個小整數（19,801 列、
  2,832 支證券、376 週中的 368 週，值 1 到 4），沒有任何官方文件定義它。它記在
  manifest 的 `dropped_adjustment_holder_counts`、留在 raw artifact 裡，不入庫。
  無來源語意的欄位不呈現成資料（CLAUDE.md 的來源欄位規則）。

### 4. 占比的上限搬到知道角色的地方

`ownership_percent` 原本是 `BETWEEN -100 AND 100`。發布者不同意：合計（分級 17）
在檔案庫裡有 158 列超過 100，橫跨 74 個資料日期、49 支證券，最高 `135.00`
（00663L，2022-11-25）。這些 security-week 的人數與股數都正常，卻因為一個我們
自己加的天花板而完全無法儲存。

實測支持的界線是逐角色的：分級 1-15 從未超過 100，分級 16 的絕對值最大 35.90，
分級 17 最高 135.00。所以 migration `c9a4e7b21d58` 把表層 CHECK 降為
`ownership_percent >= -100`，把「holding 不得超過 100」放進本來就知道角色的
row trigger 與 writer 的 profile 驗證，合計不設上限、照發布值存。

降級在有任何一列超過 100 時，在動任何資料之前就失敗：收窄 CHECK 會留下沒有任何
insert 能重現的已發布歷史（CLAUDE.md §81）。

### 5. 無法構成分布的證券自己隔離，不拖累整週

`2023/20231020.7z` 是一個在 1.5 MiB 邊界被截斷的下載，比前後週少 562 支證券，
最後一支（8162）只剩兩個分級、最後一列還被切掉一半。這一週補不回來：OpenData
只供應最新週，入口網站只回溯約一年，`shareholding.bak` 的同週副本被過濾到 1,777
支證券、而且每支只剩分級 1-15（16 與 17 被剝掉），再次證明它不是來源。

決定（owner，2026-09-22）：截斷之前的 2,786 支完整證券照常匯入——已發布的事實
仍然是事實——被切斷的那一支進 `import_quarantine`，manifest 記 `truncated_payload`
並帶一筆 warning。整檔 fail closed 會丟掉三千多支證券的完整分布，而那不是資料
的問題。逐列隔離沿用 ADR-0022 §8 的形狀。

### 6. 不從這個檔案註冊證券

TDCC 為它保管的每一個代號編表，包含權證、受益證券等遠超 v1 範圍（上市／上櫃）的
代號。已經持有的證券寫 snapshot，其餘只在 manifest 計數（`securities_outside_
the_v1_universe`）。身分繼續由交易所 feed 決定（CLAUDE.md §30、§75），否則一個
保管機構的檔案會替我們決定證券宇宙。

### 7. 發布時間只來自 `tdcc_weekly@1`

資料日期 的那一週在次週日 12:00（Asia/Taipei）解析為可知。這條規則出自 ADR-0020
§3 決策 2，依據是舊系統週日 10:20 的工作加上緩衝，而不是 TDCC 公布的時程表——
audit 找不到任何公布的時程。bulk 檔與入口網站都不帶發布時刻，所以這是這個資料集
唯一的發布時間。`first_capture` 真正第一次看到某週時另外寫 `capture_bound`；
第一次看到的時間晚於規則，就為那些列推翻規則，與 ADR-0020 §2 一致。

## 後果

* Step 24-b 可以直接走這條路徑做 376 週的回補，只需要加每週的 coverage cadence、
  農曆年休市分類與舊系統對帳。
* 既有的 TDCC 儲存契約只有一處放寬（占比上限），且降級受保護。已存的列不受影響：
  目前沒有任何 `tdcc_distribution` 列。
* 2023-10-20 永久是一個證券數偏少的週。它在 manifest 與 audit §4.9 都有記載，
  Step 24-b 的 coverage 報告要把它分類為有記載的來源缺陷，而不是我們的缺口。
* 分級 16 的 bulk 人數欄如果哪天出現官方定義，可以在不改識別與既有列的前提下
  新增欄位；在那之前 raw artifact 是它唯一的去處。
