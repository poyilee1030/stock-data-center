# Monthly Revenue

MOPS `t21sc03`, one page per market, month and issuer kind. The measured source
facts are in `docs/source_field_audit.md` §4.7 and §7; the storage design is
ADR-0027 "35-c 定案".

## Storage

`monthly_revenues` holds one append-only row per
`(stock_id, source, revenue_month)`, where `source` is `mops_t21sc03_sii` or
`mops_t21sc03_otc` and `revenue_month` is the first day of the month. A changed
published value is a later row; the earlier one stays.

**Amounts are TWD.** The page states 單位：千元, a page-level constant, so the
adapter builds each amount as `SourceRevenueAmount` with an explicit
`RevenueScale.THOUSAND` and stores it ×1,000; no stored figure has a fraction.
The unit is never inferred from magnitude (CLAUDE.md §72), and no currency
column is stored.

**The published comparatives are observed.** 上月營收, 去年當月營收, 當月累計營收,
去年累計營收, the three percentages and 備註 are published in the same row as
當月營收 and read by legacy consumers (audit §4.7, §6). They are stored exactly
as published and never reconciled against our own series; the 2026M06/M07 pair,
where 11 of 1,846 companies disagree, is the regression fixture (audit §7.3).
`monthly_revenue_growth:v1`, which would have recomputed them, leaves v1 with
that decision (ROADMAP §16).

## Pages

A market-month is two pages, `_0` domestic and `_1` foreign/KY, one job each,
four jobs in all. A company is on exactly one of them: one company on both
would give one key two alternating values from one source (CLAUDE.md §30).

`t21sc03` is regenerated by issuer status, so the source rewrites its own
history: a month's page lists the issuers that hold that status now. An issuer
that has since left both markets is missing from the 2020 page too, even though
legacy recorded it then. Such an issuer is outside today's universe
(ADR-0026); `pub` and `rotc` are refused at the adapter boundary.

A month counts as complete only after a fetch on or after 00:00 of the first
day of the month after next: issuers file by the 10th, and every month 13 to 311
domestic issuers file after it. A page fetched before then is fetched again.

## Publication

The official pages carry no publication instant, and publication differs by
issuer, so a rule would be look-ahead: `published_at` is stored on each key's
first row, and NULL is Market-PIT invisible.

- **From now on**, a `first_capture` fetch stores its own fetch instant; any
  other purpose proves nothing and stores NULL (CLAUDE.md §32).
- **History** was carried over from v1 by Step 35-c-1, which took it from the
  legacy `market.csv` (audit §7.1, §7.4, §7.5):

| Window | What the file holds | What `published_at` is |
| --- | --- | --- |
| 2020M01–2026M01 | a recovered announcement date beside today's corrected value | the end of that day in market time; the statutory 10th where the date is still the 10th |
| 2026M02 onward | the legacy 22:45 job's own first-seen date and the value it saw | the end of that day, on a row of that value |

The bound is the end of the archive's day: the file dates rows to the day, and
a bound that is slightly late is safe where an early one is not. The `_1`
foreign and KY issuers the archive never held keep NULL, 8,952 rows.

For 2026M02 onward, the legacy first-captured value comes before MOPS's current
value when the two differ: the correction is the later row, public from its own
`recorded_at`, so a query before it answers the value that was public then.
